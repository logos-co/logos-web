<p><strong>TLDR</strong>: We have just shipped two important features to The Waku Network that offer more granularity for RLN rate-limiting and add support for stateless light clients.</p>
</blockquote>
<h2 id="introduction-to-the-waku-network">Introduction to The Waku Network</h2>
<p>Waku launched The Waku Network last <a target="_blank" rel="noopener noreferrer" href="https://thedefiant.io/news/press-releases/waku-launches-first-decentralised-privacy-preserving-dos-protections-for-peer-to-peer-messaging">December 2023</a>. A first-of-its-kind decentralized network focused on privacy and censorship resistance, running an opinionated instance of the Waku protocol with the following features:</p>
<ul>
<li>Generalized messaging network, that allows point-to-point or broadcast communications, preserving the identity of the sender, not linking its messages to any identity or IP address.</li>
<li>A decentralized and permissionless network acting as a common infrastructure, not controlled by a single actor and open to anyone, both users and operators.</li>
<li>Rate-limited to ensure a fair usage of resources. It uses RLN (Rate Limiting Nullifiers) that leverage zero-knowledge cryptography to guarantee users adhere to a rate limit without compromising their privacy. Anyone can register in the smart contract, currently deployed in Sepolia testnet, by paying a small fee.</li>
<li>Support for light clients, defined as resource-restricted devices that interact with the protocol without participating in message routing.</li>
<li>Incentivized, both non-economic (reputation mechanism already implemented) and economic (crypto incentives currently under research).</li>
</ul>
<p>Over the last months, we detected a few limitations introduced by the usage of RLN for rate limiting, and we have been working hard to address them. As a result, we are proud to announce that the following new features are live in The Waku Network:</p>
<blockquote>
<p>We are excited to announce that last 3rd of July 2024, we introduced the following features, part of release <a target="_blank" rel="noopener noreferrer" href="https://github.com/waku-org/nwaku/releases/tag/v0.30.1">v0.30.1</a>.</p>
</blockquote>
<ul>
<li><strong>Better rate-limiting:</strong> The previous rate-limiting mechanism (RLN-V1) only allowed to rate limit <code>1</code> message every <code>y</code> seconds. This wasn&#x27;t practical and it&#x27;s why we have just shipped RLN-V2, which allows nodes to rate limit <code>x</code> messages every <code>y</code> seconds.</li>
<li><strong>Stateless light clients:</strong> The main problem light clients had, was that they needed to sync and keep track of the Merkle tree that stored all memberships. This was slow and required both bandwidth and resources, a no-go for resource-restricted devices. After some changes in the smart contract, we now store the whole Merkle tree on it, which allows light clients to be stateless. The smart contract now provides all the required information. No need to sync. No need to keep state.</li>
</ul>
<h2 id="better-rate-limiting">Better rate-limiting</h2>
<p>One of the main limitations of the previous rate-limiting mechanism (aka RLN-V1), was that it only allowed to rate limit <code>1</code> message every <code>y</code> seconds. This wasn’t practical since a low value would allow too many messages, and a high one would make the network unusable in practice.</p>
<p>Over the last months, we have been working hard in integrating <a target="_blank" rel="noopener noreferrer" href="https://github.com/vacp2p/rfc-index/blob/a5b24ac0a27da361312260f9da372a0e6e812212/vac/raw/rln-v2.md">RLN-V2</a>, which allows nodes to rate limit <code>x</code> messages every <code>y</code> seconds. This gives us extra granularity, making it more usable in practice.</p>
<blockquote>
<p>The rate-limit <strong>was 1 message per second.</strong> Now with RLN-V2 The Waku Network allows more granularity, initially set to <strong>100 messages every 10 minutes</strong> for each member. There are plans to extend this to different “tiers” where each limit will have a different cost.</p>
</blockquote>
<p>But how does it work? There are two main components:</p>
<ul>
<li>🗝️+🔑: The RLN membership, which is made of a public (🔑) and private key (🗝️), whose holder can use to “sign” messages valid in the network. Anyone can register one in the smart contract.</li>
<li>📧: The RLN proof and nullifier. It allows anyone to verify that a message is valid according to the rules. The nullifier acts as a stamp that is attached to each message and allows nodes to rate-limit the sender, while being privacy-preserving.</li>
</ul>
<p><img alt="rlnv2-stamps" src="/media-images/waku_7975748027b9_rlnv2_stamps_9fe12cb6ed-43427eac-750.webp" srcset="/media-images/waku_7975748027b9_rlnv2_stamps_9fe12cb6ed-43427eac-750.webp 750w, /media-images/waku_7975748027b9_rlnv2_stamps_9fe12cb6ed-43427eac-1400.webp 1400w" sizes="(max-width: 767px) calc(100vw - 32px), 700px" width="1662" height="634" loading="lazy" decoding="async" /></p>
<p>Each membership (🗝️+🔑) is virtually given 100 stamps (📧) every 10 minutes to spend on credits to send messages. Every sent message consumes a stamp. Nodes in the network count them and reject messages with none or repeated ones. And nodes are incentivised via reputation to not relay messages with invalid stamps.</p>
<p>This protects The Waku Network against Denial of Service attacks while preserving the privacy of the sender, since it doesn’t reveal its membership, IP address or any other information to anyone.</p>
<p>The pricing mechanism is yet to be set. By now a user wanting to register a membership just has to pay just the transaction fees. There are plans to extend this to different “tiers” where each message limit will have a different cost. Note that the time window <code>y</code>, also called epoch size, is a network parameter common to all nodes that can&#x27;t be configured individually.</p>
<h2 id="stateless-light-clients">Stateless light clients</h2>
<p>We define light-clients as the nodes that interact with The Waku Network to send or receive messages but don’t participate in routing nor offer other capabilities such as storing historical messages. In other words, they are nodes running in resource-restricted devices interacting with the network but not contributing to it. Think of a client running on a phone or browser.</p>
<p>In order to send a message, the light client must attach a proof/stamp (📧) to the message (💬) as explained before. This stamp is in reality an RLN zero-knowledge proof to prove that its valid and respects the rate-limit.</p>
<p>Up until now, there was a lot of friction for light clients, since in order to get the stamp (📧), they required the whole Merkle tree storing all memberships. Synchronizing this tree consumed resources: bandwidth, storage, and computation, which was a no-go for light clients.</p>
<p>However, we are proud to announce that now the Merkle tree is stored onchain. This removes the need for light clients to sync the tree. The contract provides all the required information. No need to sync. No need to keep state anymore.</p>
<blockquote>
<p>The RLN membership Merkle tree is now stored in the smart contract, which allows light clients to be stateless. No need synchronize the Merkle Tree. The contract provides all required information via <code>merkleProofElements()</code> (to generate proofs) and <code>root()</code> (to verify them).</p>
</blockquote>
<p>Let&#x27;s see an example. A membership is represented by two keys:</p>
<ul>
<li>🔑: A public one, stored as a leaf in a Merkle tree</li>
<li>🗝️: A private one, that gives the right of the holder to publish valid messages.</li>
</ul>
<p>Now the smart contract provides both:</p>
<ul>
<li>🫚: Merkle root of the tree containing all memberships 🔑, accesible by <code>root()</code></li>
<li>🌲: Merkle proof of a given membership 🔑, accesible by <code>merkleProofElements(leaf)</code></li>
</ul>
<p>Since root (🫚) and proofs (🌲) are now publicly available in the smart contract, light clients don’t have to calculate these themselves. These allows seamless proof generation (for publishers) and verification (for subscribers):</p>
<ul>
<li>🗝️+🌲 = 📧 Using its private key (🗝️) and the leaf Merkle proof (🌲) a publisher can generate the stamp (📧) that is attached to the message (💬).</li>
<li>🫚+📧 = ✅/❌ The Merkle root (🫚) and the included stamp (📧) of the message (💬), can be used by the subscriber to verify if the message is legit to accept (✅) or reject (❌) it.</li>
</ul>
<p><img alt="rln-light" src="/media-images/waku_aa07c9140f94_rln_light_07fdf010df-75ee1fd0-750.webp" srcset="/media-images/waku_aa07c9140f94_rln_light_07fdf010df-75ee1fd0-750.webp 750w, /media-images/waku_aa07c9140f94_rln_light_07fdf010df-75ee1fd0-1400.webp 1400w" sizes="(max-width: 767px) calc(100vw - 32px), 700px" width="2772" height="1680" loading="lazy" decoding="async" /></p>
<p>Note that both <code>merkleProofElements(leaf)</code> and <code>root()</code> are free to call. They are <code>view</code> functions that don’t modify any state. Moreover, they don’t consume much resources and should work in any RPC provider.</p>
<p>Note also that they are lazily evaluated, meaning that they are calculated on each call based on some intermediate stored leafs. This allows to save lots of gas. Insertions are expected to cost between 100k and 200k gas, hitting rarely more than that in <code>2^n</code> leafs.</p>
<p>The contract is currently deployed in Ethereum Sepolia testnet, but its expected to move to a Layer 2 where gas would be even cheaper.</p>
<h3 id="join-the-waku-network">Join The Waku Network</h3>
<p>Both of these features are live in The Waku Network, so if you want to test them out, join The Waku Network by using <a target="_blank" rel="noopener noreferrer" href="https://github.com/waku-org/nwaku-compose">nwaku-compose</a>. As simple as cleaning up your previous configuration and running two commands.</p>

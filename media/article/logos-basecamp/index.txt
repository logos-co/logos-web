<h1>Basecamp: Your Base of Operations on the Logos Frontier</h1>

<p>
  Every expedition needs a base of operations. A private, secure shelter already equipped with supplies and communications, so you can spend your time exploring, not building from scratch.
</p>

<p><strong>That's Basecamp.</strong></p>

<p>
  Basecamp is a ready-to-run distribution that you deploy on your own hardware, under your control. From the moment it’s installed, you’re standing on your own ground, not connecting to someone else’s infrastructure. The Logos Runtime is already running locally, core modules are loaded, and essential applications — wallet, messenger, file sharing, blockchain explorer — are ready to use from day one.
</p>
<p>
  This changes the relationship between the user and the system. When everything runs locally, privacy is the default state. Because you control the environment, you control your data.
</p>
  
<hr>

<h2>What Basecamp actually is</h2>

<p>
  Basecamp is the launcher and unified surface of the Logos stack. It is an executable that wraps the Logos Runtime and does three things:
</p>

<ol>
  <li>Initialises the Logos Core environment on startup</li>
  <li>Discovers and loads UI plugins from whatever modules are installed</li>
  <li>Presents a unified surface where users interact with everything</li>
</ol>

<p>
  That last point is important to understand. Basecamp doesn't <em>do</em> the work, it <em>surfaces</em> it to users. The logic for the wallet lives in the blockchain module, messaging in comms, and file-sharing in storage. Basecamp is the place all of those show up, consistently, in one place.
</p>

<p>
  Think of it as the user-facing access point for a modular, unified stack — the thing that turns a collection of powerful, interoperable modules into a coherent experience.
</p>

<h2>Local-first, by conviction</h2>
 
<p>
  Every layer in the stack you're about to see — Runtime, Network, Modules, App Backends — runs on <em>your</em> machine. Not on a cloud server you rent, not behind an API you call, not in a data centre that logs your queries, graphs your social connections, and sells the patterns. 
</p>

<p>
  The entire stack is local-first infrastructure, operated as a peer-to-peer network where your node is a full participant, sourcing and leveraging the modules it needs to run your application.
</p>
 
<p>
  Centralised services are custodial by nature: they require your trust and can access your metadata, if not your actual data, in return for convenience. The trade-off is rarely made explicit. Who you message, when, how often, from where — that metadata is often more revealing than the content itself, and conventional architectures funnel all of it through chokepoints that can observe, store, and monetise it. 
</p>
<p>
  Basecamp's stack is designed around the opposite assumption. The P2P network layer means your messages, files, and transactions flow between peers, not through a single relay. The modules run locally, so your wallet state, your chat history, and your file index never leave your device unless you choose to share them. There is no sign-up, no account on a remote server, no quiet background sync to infrastructure controlled by a single entity.
</p>

Basecamp is one of three ways in. The diagram illustrates this structure. Pick a use case from the tabs and the slice of the stack it leans on lights up, with live arrows tracing the data flow.
</p>

<h2>What you get out of the box</h2>

<p>
  The default Basecamp installation ships with <strong>Simple Apps</strong> for each core module:
</p>

<ul>
  <li><strong>Wallet</strong> — managing accounts and assets on the Logos blockchain</li>
  <li><strong>Chat interface</strong> — encrypted messaging via the Logos comms layer</li>
  <li><strong>Filesharing tool</strong> — private, decentralised file storage and sharing</li>
  <li><strong>Blockchain / LEZ explorer</strong> — inspect the chain, transactions, and execution zones</li>
</ul>

<p>
  The <em>Default Basecamp user</em> tab in the diagram shows what this looks like in motion: each Simple App is a UI plugin at the top of the Basecamp zone, and each one lights up its own slice of the stack <em>in parallel</em>. The wallet rides LEZ → Blockchain. The messenger rides Chat → Delivery. The dashboard reads straight from the blockchain. Same launcher, several flows, no duplication.
</p>

<p>
  The single-purpose tabs — such as <em>DEX trader</em>, <em>Private messaging</em>, and <em>File sharing</em> — isolate each of those flows. The arrows show the direction of dependency: a chat user's bytes flow through Chat → Delivery → P2P, never touching the blockchain. A trader's flow through LEZ → Blockchain, never touching Storage. This flow is what makes the Logos stack truly modular and interoperable.
</p>

<p>
  These aren't separate apps stitched together; they load from Basecamp's unified shell using a consistent design system and are discovered automatically by the Package Manager.
</p>

<hr>

<h2>Module-agnostic by design</h2>

<p>
  Basecamp doesn't care which modules you have installed. It discovers them, loads their UI plugins, and surfaces them to you whatever the configured profile contains.
</p>

<p>
  This is an intentional design feature. The stack composition is defined by which modules are selected, not by the launcher. This allows a developer building a specialised Logos distribution to swap the module set entirely, using only what they need. Basecamp simply loads what is there, offering one launcher for many possible stack configurations.
</p>

<p>
  The <em>Atomic swap</em> tab in the diagram makes this case visually. A trustless cross-chain swap composes the existing Swaps module on top of LEZ (Logos side) with a <em>proposed</em> Monero module (XMR side, shown with a dashed border). The DEX UI doesn't change; the user's path through the stack does. Adding a new module with new capabilities requires no work on the part of the launcher, which just traces the data flow through the new stack configuration.
</p>

<p>
  This composability is where Basecamp draws from its inspirations: the <a href="https://github.com/ethereum/mist">Mist Browser</a> was an early reference point — an entry-level gateway into an ecosystem — and <a href="https://leechcraft.org/">LeechCraft</a>, a modular live environment where every capability is a plugin. Basecamp's ambition is to go further: composability at the ecosystem layer, built on a privacy-preserving, decentralised foundation.
</p>

<hr>

<h2>Three ways in, one stack</h2>

<p>
  Basecamp is the default launcher, but it is not the only way for users to access the Logos stack. The three header zones at the top of the diagram show the available options:
</p>

<ul>
  <li><strong>Logos Basecamp</strong> — the unified launcher most users want. Discovers modules, surfaces their UIs, gets out of the way.</li>
  <li><strong>Standalone App</strong> — when you don't want a launcher at all. A single binary ships with its own UI and just the modules it needs. Useful for purpose-built clients (the <em>Standalone app</em> tab walks through a focused DEX example) where Basecamp's discovery model would be unnecessary overhead.</li>
  <li><strong>Headless Node</strong> — no UI surface, just a CLI. Useful for servers, validators, or infrastructure. The <em>Headless node</em> tab shows that headless can drive modules at any depth — a validator drives LEZ on top of Blockchain, a storage provider drives Files on top of Storage, and a relay drives Chat on top of Delivery. Runtime up, P2P peers connected.</li>
</ul>

<p>
  The choice between the three is about what <em>surface</em> you want, not what's underneath.
</p>

<hr>

<h2>For developers: QML is the easy path</h2>

<p>
  Basecamp is also where the module-building story meets deployment. Once you've scaffolded a module with the <code>lm</code> CLI and the module-builder tooling, Basecamp is how you actually run it. The <em>Module developer</em> tab in the diagram traces the path involved: the new module gets detected by the Package Manager module, listed in the Package Manager UI, and auto-loaded by Basecamp on its next launch. The rest of the stack is what your module <em>composes against</em>.
</p>

<p>
  The team is moving toward a QML-only UI layer for module frontends, with the C++ application backend running in a separate process. The practical upshot of this approach is that if you build your module UI in QML, it works in Basecamp without friction. The system is intentionally designed this way — the examples and tooling are being built to make QML the path of least resistance.
</p>

<p>
  Current support: <strong>Linux and macOS</strong>, with <strong>C++</strong> for module development. Windows, Android, iOS, and additional SDK languages (Rust, JS, Nim) are in active development.
</p>

That's when Basecamp stops being a developer testing surface and begins to resemble the first-class user experience the frontier deserves.

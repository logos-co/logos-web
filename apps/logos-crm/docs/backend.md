# Logos CRM — Backend Specification

## 1. Service boundaries

The backend has three layers:

1. Next.js Route Handlers: HTTP parsing, authentication, Zod validation, and response mapping.
2. Services: business rules, authorisation checks, transactions, and orchestration.
3. Integrations/jobs: CiviCRM import, email, Discord, and other external systems.

Do not add a generic repository layer or base classes around Drizzle. Focused query modules may encapsulate a complex reusable query, but services can use typed Drizzle queries and transactions directly. Route Handlers must not contain multi-step business logic or raw SQL. Server Components call services directly; they must not call the app's own HTTP endpoints.

All database, service, job, and authorisation modules live under `apps/logos-crm/src/server` and are marked server-only. Client code imports browser-safe Zod schemas and inferred DTO types only; it must not import a server module.

The auth seam accepts requests only when the Infra verification header matches the configured secret and both subject and email headers are present. Infra strips all client-provided copies before injecting trusted values. The immutable subject identifies the user; unknown valid subjects become pending users and receive `403 USER_PENDING_APPROVAL`. An idempotent CLI command bootstraps the first admin without a default password or public setup endpoint.

Role and record-scope rules are defined once as server-authored CASL abilities. A shared server-only auth function resolves the actor and ability for Route Handlers and services; services remain the enforcement boundary. Drizzle queries must still apply record-scope predicates so unauthorised rows are never loaded merely to be rejected afterwards. UI checks may consume a safe capability projection for presentation only and never replace server checks.

## 2. Database model

Drizzle table definitions are the persistence schema source. PostgreSQL constraints and indexes are declared with Drizzle where supported; checked-in custom SQL is limited to PostgreSQL features that Drizzle Kit cannot express. Browser-safe Zod schemas define API and form contracts without importing Drizzle tables into client bundles. Server-only migration and persistence validation may derive schemas with `drizzle-zod`; explicit refinements are limited to cross-field business rules and safe API projections.

The initial PostgreSQL schema contains:

| Table                                                 | Purpose                                            |
| ----------------------------------------------------- | -------------------------------------------------- |
| `users`, `user_roles`                                 | Local identities and fixed role assignments        |
| `teams`, `user_teams`                                 | Team definitions and membership                    |
| `people`, `contact_methods`                           | People and normalised contact channels             |
| `organisations`                                       | Organisations and normalised search fields         |
| `person_organisation_relationships`                   | Typed people-to-organisation links                 |
| `cases`, `case_people`, `case_organisations`          | Cases and related CRM entities                     |
| `case_assignments`                                    | Current and historical ownership                   |
| `case_type_definitions`, `case_status_definitions`    | Case types and status catalogue                    |
| `case_status_history`                                 | Status history                                     |
| `case_stage_history`, `ecodev_case_details`           | Ecodev fields and stage history                    |
| `catalogue_values`                                    | Other controlled CRM values                        |
| `activities`, `activity_mentions`                     | Timeline entries and resolved mentions             |
| `tasks`                                               | Assigned follow-ups and due dates                  |
| `notification_preferences`, `notification_deliveries` | Delivery choices and auditable results             |
| `discord_identities`                                  | Optional CRM-user-to-Discord mapping               |
| `external_identities`, `entity_merges`                | Source IDs and duplicate merge history             |
| `import_runs`, `import_errors`                        | Import progress and row-level failures             |
| `export_jobs`                                         | Export request, filters, file metadata, and expiry |
| `audit_events`                                        | Append-only redacted mutation history              |

Required conventions are expressed in the Drizzle schema and emitted through Drizzle Kit migrations:

- UUID primary keys generated by the database or server;
- UTC timestamps stored as `timestamptz`;
- `created_at` and `updated_at` on mutable records;
- soft archive/status fields for business records instead of destructive deletion;
- a unique source-system/entity/source-ID constraint on external identities;
- indexes for searchable names, email, status, assignee, and updated time;
- foreign keys with an explicit deletion policy;
- migrations generated, checked, committed, and applied with Drizzle Kit through the release process.

The concrete columns, ownership rules, merge behaviour, visibility model, and indexes are defined in [`data-model.md`](data-model.md).

Use typed subtype tables for case-type-specific fields. Do not use a generic entity-attribute-value table for Ecodev fields: these fields require validation, indexing, filtering, and reporting. `cases` contains common case fields; `ecodev_case_details` contains Ecodev-only fields.

## 3. Core state machines

### Case status

Initial statuses: `new`, `in_progress`, `waiting`, `resolved`, `closed`, `archived`.

Allowed transitions are enforced in the service layer and recorded in both `case_status_history` and `audit_events`. A transition can include a required reason. `archived` is admin-only and cannot be selected as an active workflow status.

### Migration run status

`pending` → `previewing` → `ready` → `running` → `completed` or `failed`; `running` may transition to `cancelled` through an explicit admin action.

### Ecodev sales opportunity

An Ecodev case uses the common case title, owner, team, source, priority, and status fields plus an `ecodev_case_details` row containing `stage`, `substatus`, `business_unit`, `platform`, `tags`, `summary_notes`, `last_contact_at`, `validation_status`, `validated_at`, and `validated_by_user_id`.

| Field                  | Storage          | Constraint                                    |
| ---------------------- | ---------------- | --------------------------------------------- |
| `stage`                | text code        | required, versioned catalogue value           |
| `substatus`            | text code        | optional, must belong to the selected stage   |
| `business_unit`        | text code        | required catalogue value                      |
| `platform`             | text array       | zero or more catalogue values                 |
| `tags`                 | text array       | normalised lowercase slugs, deduplicated      |
| `summary_notes`        | text             | optional, maximum 10,000 characters           |
| `last_contact_at`      | `timestamptz`    | optional, cannot be unreasonably future-dated |
| `validation_status`    | text code        | required catalogue value                      |
| `validated_at`         | `timestamptz`    | required when validation is completed         |
| `validated_by_user_id` | UUID foreign key | required when validation is completed         |

Stage and substatus values come from versioned server-side configuration and are validated as an allowed pair. Changes to stage/substatus write `case_stage_history`; status changes write `case_status_history`; owner/team changes write assignment and audit records in the same transaction.

### Export job status

`pending` → `running` → `completed` or `failed`; completed exports transition to `expired` after the configured retention period.

List endpoints use `page`, `page_size`, `q`, resource-specific filters, `sort`, and `order`. Zod schemas coerce and validate these values. The default page size is 25 and the maximum is 100.

All v1 lists use page-based pagination. Sort fields and filter keys are resource-specific allowlists. Global search returns grouped results with a small fixed limit per entity type rather than pretending to be another list endpoint.

Person and organisation create/update contracts include their full contact-method collection and replace it transactionally after validation. Case create/update contracts use a discriminated union by `case_type`, include related people/organisation link collections, and reject Ecodev fields for another case type. Activity and task creation require exactly one parent identifier.

Successful mutations return the updated resource. Errors use:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "One or more fields are invalid.",
    "fields": { "status": "Unsupported transition." },
    "request_id": "req_..."
  }
}
```

Supported error codes include `UNAUTHENTICATED`, `USER_PENDING_APPROVAL`, `FORBIDDEN`, `NOT_FOUND`, `VALIDATION_ERROR`, `CONFLICT`, `DUPLICATE`, and `INTERNAL_ERROR`.

## 5. Mutation and consistency rules

- Every mutation resolves the actor from the authenticated request.
- Case updates, assignment changes, activity creation, and audit events commit with `db.transaction(...)`.
- `PATCH` requests accept an `If-Match` version or equivalent `updated_at` token and return `409 CONFLICT` for stale edits.
- Retryable external mutations require an `Idempotency-Key` header.
- Notification delivery rows and Graphile Worker jobs are inserted in the same PostgreSQL transaction as the business mutation.
- The server parses note mentions and stores resolved users in `activity_mentions`; client autocomplete is not trusted as the source of truth.
- A mention is rejected if the mentioned user cannot access the linked record; notifications never grant access.
- Mention notifications are deduplicated by activity, mentioned user, and delivery channel.
- Notification links use `CRM_PUBLIC_URL` and canonical `/cases/:id` routes; no linked case is publicly accessible.
- Graphile Worker claims jobs safely; delivery tables record attempts, errors, and completion time.
- Merge operations move links and external identities, archive the duplicate, and write an audit event atomically.
- User suspension takes effect on the next request and queued exports/notifications re-check the current user state before processing.
- CiviCRM imports upsert only by `(source_system, source_id)` and never by email alone.

## 6. Jobs and integrations

Initial job types:

- `send_email_notification`;
- `send_discord_notification`;
- `send_task_reminder`;
- `generate_export`;
- `expire_export`;
- `import_civicrm_batch`;
- `reconcile_civicrm_batch`;
- `expire_stale_import`.

Graphile Worker's built-in cron support scans due tasks and expires files. Delayed work uses `runAt`; deduplication and rescheduling use namespaced `jobKey` values; serial external operations use low-cardinality queue names. No separate cron container or Redis scheduler is introduced.

Each task validates its payload with Zod and configures Graphile Worker's `maxAttempts`, `jobKey`, `jobKeyMode`, `runAt`, priority, and queue options as needed. Graphile Worker supplies exponential retry and graceful shutdown; do not implement a second retry loop or scheduler. Application delivery tables retain business-level outcomes because successful Graphile jobs are removed from the queue. Graphile Worker is the queue; there is no application outbox dispatcher, Redis, scheduler service, or second broker.

Email reuses the existing `admin-acid` Nodemailer and SMTP contract: `SMTP_SERVER`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, and `SMTP_TLS_ENABLE`, with 10-second connection, greeting, and socket timeouts. The credentials are supplied by Infra; the CRM does not run an SMTP container or add a provider-specific API. `SMTP_FROM` is server configuration and cannot be overridden by request data. Discord delivery uses the Discord REST API through the platform `fetch`; a Discord SDK is unnecessary for v1. Disabling Discord must not block core CRM mutations or jobs.

Mention notification flow:

1. Store the note and resolved `activity_mentions` in one transaction.
2. Insert delivery records and enqueue email and, when enabled and mapped, Discord Graphile jobs according to the mentioned user's preferences.
3. Send the actor, case title, a safely truncated note excerpt, and `/cases/:id` deep link.
4. Record delivery attempts and final status without copying secrets or full note text into logs.

`discord_identities` maps a CRM user to a Discord user ID and optional default channel ID. Mapping is administered locally; the CRM does not depend on Discord as an identity directory.

Discord jobs escape user-controlled text, respect `Retry-After`, use bounded retries, and store only status/error codes. Missing or deactivated mappings create a visible skipped delivery rather than failing the originating CRM mutation.

Reporting uses `cases`, `case_status_history`, `case_stage_history`, assignments, teams, sources, and Ecodev details. Metric definitions are:

- funnel count: cases created in the selected cohort grouped by their status at the explicit `as_of` time;
- progression: cases in the selected created cohort that entered the destination stage divided by cases in that cohort that entered the source stage;
- median time in stage: median interval between consecutive stage-history rows;
- active onboarding: cohort cases whose status at `as_of` maps to the active-onboarding category;
- approved versus redirected: cohort cases whose status at `as_of` maps to the `approved` or `redirected` outcome category;
- growth over time: cases created in the selected timezone and period bucket;
- owner/team breakdown: assignment active at `as_of`, with an explicit unassigned bucket.

Every report request requires `cohort_from`, `cohort_to`, `as_of`, and an IANA timezone. `as_of` cannot precede the cohort start or exceed the current server time. Catalogue reporting categories are versioned by effective time so editing a display label does not rewrite historical meaning. Imported cases without trustworthy history are included in current funnel counts but excluded from transition-duration metrics and reported in a coverage count.

CSV and XLSX exports use the same Drizzle query, filters, CASL field projection, and timezone as their source list/report. All exports run as Graphile Worker jobs. CSV output uses PapaParse `unparse`, UTF-8 with BOM, and a pre-serialisation guard for spreadsheet formula prefixes. XLSX output uses ExcelJS. Files are written to a protected Docker volume, served only through the authenticated download route, and deleted after 24 hours by default.

Exportable resources and default columns are versioned server-side. Clients send a resource name, format, filters, sort order, timezone, and allowed column IDs; they cannot submit SQL, raw field paths, or arbitrary filenames. The worker repeats authorisation against the requesting user before generating the file.

Imports accept UTF-8 CSV with optional BOM through `multipart/form-data`, with a default 25 MB and 50,000-row limit. PapaParse performs row parsing and reports parser errors; derived Drizzle/Zod schemas validate mapped rows; Node's `crypto` computes the SHA-256 checksum. Preview stores only a protected temporary file plus safe row errors. Commit requires the preview ID, matching checksum, and idempotency key. The UI follows the established `admin-acid` progress/error pattern, while the server remains authoritative.

The CiviCRM integration is read/import-only until a separate write-synchronisation decision is approved. The public funnel remains on its existing path during v1.

## 7. Security and observability

- Validate every request body, query parameter, path identifier, and declared response through shared Zod contracts.
- Enforce maximum body sizes and reasonable query limits.
- Infra owns edge rate limiting; the CRM does not add a Redis-backed rate limiter.
- Never log access tokens, secrets, or full personal records.
- Never log full email addresses, telephone numbers, note bodies, import rows, or export contents.
- Attach a request ID to logs and API error responses.
- Record authorisation failures without exposing sensitive record existence where policy requires concealment.
- Expose web readiness and worker/database health checks.
- Emit structured Pino events for request failures, job lag/failures, import throughput, and reconciliation failures so Infra can collect them without an application-owned monitoring stack.
- Audit exports, merges, role changes, catalogue changes, archives, and permanent-deletion actions.
- Personal-data retention, anonymisation, and hard deletion run through explicit admin workflows; archive is not treated as deletion.

## 8. Backend test matrix

- unit tests for state transitions, CASL ability definitions, identity mapping, and import mapping;
- auth tests for stripped/forged headers, proxy-secret rotation, email changes, and suspension;
- Drizzle query integration tests against PostgreSQL migrations using deterministic `drizzle-seed` fixtures;
- service tests for transaction boundaries, conflicts, idempotency, and audit events;
- Route Handler integration tests for authentication, validation, error shapes, and pagination;
- worker tests for retries, deduplication, cancellation, and permanent failure;
- migration tests that import the same fixture twice and compare stable counts;
- report tests for cohort progression, status duration, outcomes, unassigned ownership, and timezone boundaries;
- export tests for filter parity, field redaction, CSV formula escaping, XLSX cells, expiry, and download authorisation;
- mention tests for unknown and duplicate usernames, preferences, Discord mapping, retry, deduplication, and deep links;
- task tests for overdue boundaries, completion, reminder deduplication, and record permissions;
- merge tests for conflicts, relationships, source IDs, task/activity links, and rollback on failure;
- settings tests for fixed-role assignment, team deactivation, and referenced catalogue values.

## 9. Self-hosting requirements

The backend must ship with:

- a production Dockerfile and a minimal runtime image;
- the canonical three-service `docker-compose.yml` for web, worker, PostgreSQL, and the protected file volume;
- PostgreSQL migration and rollback procedures based on checked-in Drizzle Kit SQL;
- health and readiness endpoints suitable for Docker Compose health checks;
- no runtime requirement for Vercel, hosted PostgreSQL, hosted Redis, hosted queues, or hosted authentication;
- compatibility with the existing Infra SMTP contract, protected import/export volume, and optional Discord adapter;
- a backup and restore procedure using standard PostgreSQL tooling.
